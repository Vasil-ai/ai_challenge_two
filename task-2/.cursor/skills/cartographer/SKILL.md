# Cartographer

Produce an accurate, navigable map of the **current workspace** repository. The deliverable is always:

`docs/CODEBASE_MAP.md`

Create the `docs/` directory if it does not exist. Overwrite or refresh `CODEBASE_MAP.md` so it reflects the tree as it exists now (do not preserve stale modules or removed paths).

## Principles

- **Evidence-based**: derive structure from the filesystem and real entrypoints (build files, main classes, package.json, Dockerfile, etc.), not guesses.
- **Scannable**: short sections, tables where helpful, bullet lists for boundaries and responsibilities.
- **Actionable**: call out where to change behavior (e.g. security, API contracts, migrations).

## Workflow

1. **Detect stack and layout**
   - Identify primary languages, build tools (Maven/Gradle, npm, etc.), and framework signals (e.g. Spring `Application`, `pom.xml`, `package.json`).
   - Note monorepo vs single module; list top-level directories that matter for code vs infra vs docs.

2. **Entry and configuration**
   - Record application entrypoints (e.g. `@SpringBootApplication`, `main()`), default ports, profiles, and key config files (`application.yml`, `.env.example`, Docker/K8s if present).

3. **Domain boundaries**
   - Map packages/modules to responsibilities (API, domain, persistence, integration). Name important aggregates or bounded contexts if visible from code.

4. **External edges**
   - Databases, message brokers, HTTP clients to third parties, auth providers, feature flags—only what the repo actually wires.

5. **Tests and quality gates**
   - Where tests live, CI hints (`/.github`, Maven plugins), static analysis if configured.

6. **Write `docs/CODEBASE_MAP.md`**
   - Use the template below. Omit sections that truly do not apply; say "N/A" only when the category was checked and nothing exists.

## Output template

Use this skeleton (adapt headings to the stack; keep the top-level order where possible):

```markdown
# Codebase map

> Generated by Cartographer. Last updated: YYYY-MM-DD (use the user's authoritative "today" from the session if provided.)

## Snapshot

| Item | Value |
|------|--------|
| Primary stack | … |
| Build / run | … |
| Main entry | … |

## Repository layout

High-level tree (important dirs only; use indented bullets or a compact tree).

## Runtime and configuration

How the app is started, profiles, env vars, ports.

## Architecture

Layers or modules and what each owns. Short notes on cross-cutting concerns (logging, errors, validation).

## API and interfaces

REST/OpenAPI routes, CLI, batch jobs, or public packages—group by area.

## Data and persistence

Entities, repositories, migrations (Flyway/Liquibase/etc.), important schema notes.

## Security and auth

Spring Security filters, JWT/session, roles, sensitive endpoints.

## Integrations

External systems and where they are called from.

## Tests and CI

Test layout, how to run tests locally, CI workflows if present.

## Conventions

Package naming, DTO vs entity patterns, error format, anything team-specific visible in code.

## Quick navigation

Bullet list: "To change X, start in `path/` …"
```

## After writing

- Skim the file for broken paths or references to files that do not exist.
- If the repo is huge, prefer breadth over deep file-by-file listing; deep dives belong in separate docs, not here.
